# How I built WeLook

I started by profiling the supplied compressed file as a stream and keeping a seeded 5,000-row sample for iteration. Many observations described cloud or CDN infrastructure. That made account attribution the first product decision: provider names, server locations, and scanner labels could not simply become customer facts. I chose a sales research workflow for an external attack-surface monitoring product.

My development loop was to define a small data contract, implement it with Codex, inspect sample outputs and counterexamples, then run the full pipeline and reconcile counts. Codex helped draft Python ingestion, dbt SQL, Streamlit screens, tests, and documentation. I used `uv` for repeatable dependencies, Parquet for replayable layers, and DuckDB for local processing. The full source produced 11.77 million accepted observations and a compact serving database for the hosted app.

AI saved the most time on routine implementation and on proposing checks for retries, citations, and costs. It required more correction when fluent code or prose hid an unsupported sales conclusion. Early priority logic treated vulnerability labels too similarly; inspecting the source's nested metadata led to separate scanner-verified and unverified signals. A two-file fixture also exposed case-normalised domain duplicates and source-line citation collisions. The resulting fixes preserved unique evidence IDs through gold and serving and invalidated stale AI notes.

The offline AI batches showed why generation and publication need separate steps. In an early 100-account batch, 67 outputs overstated partial domain matches and were withheld. A later 100-account batch cost about six cents, but 96 drafts failed the stricter wording gate. Nine additional briefs were individually curated for the demo, including the seven top-tier candidates; this curation does not verify ownership or technical findings.

Codex proposed draft labels for 25 evidence bundles. The comparison harness showed v5 following the decision policy more closely than v4, while none of ten unverified-direct notes passed the prose gate. The labels remain marked for independent human review. The eval therefore measures an explicit policy on a small selected set, not real-world vulnerability accuracy. Exact model responses and failures are retained so a reviewer can assess that distinction.

The weakness I would flag to a teammate is **account identity**. WeLook groups observations by domain; it does not resolve every business or verify its current service operator. The app requires a sourced company name before a researcher can mark a candidate ready for sales review, and its score represents investigation priority. The next step would be independently reviewed labels, sourced identity enrichment, and feedback from sales users before expanding automation.
