# How I built WeLook

I built WeLook as a small data platform with a sales workflow at the end, rather than starting with a dashboard. I first profiled the entire supplied compressed file as a stream and kept a seeded 5,000-row sample for fast iteration. That showed an important product risk: many records describe cloud or CDN infrastructure, so `org`, IP location, and vulnerability labels cannot simply become customer facts. I chose an external attack-surface monitoring sales use case and made account attribution and evidence review visible in the app.

My development loop was: write a narrow pipeline step, run it on the sample, inspect real counterexamples, then run it on the full source and reconcile counts. I used Codex to help draft Python ingestion, dbt SQL, Streamlit screens, tests, and documentation. `uv` made the environment repeatable; DuckDB and Parquet kept the 11.77-million-row job on one laptop. The full ingestion reconciled every source line, and the account build produced a compact serving snapshot. A second-file fixture later exposed duplicate normalised domains and source-line citation collisions; I added evidence deduplication, globally unique record IDs, and stale-AI invalidation. I kept the expensive work offline so the hosted app can be read-only.

AI saved the most time when turning a concrete data contract into working code and when suggesting checks around retries, evidence IDs, tracing, and costs. It cost more time where a plausible implementation could give a misleading sales conclusion. For example, the first score treated every vulnerability association similarly. Inspecting the nested source metadata showed that nearly all sampled associations were unverified, so I changed the model to keep and use that flag. Provider platforms caused a similar correction: matching a domain and certificate can still identify a shared service, not the business behind it. An offline 100-account batch called 67 partial-match cases `supported`, so I withheld those outputs and published only 33 cautious notes after source-ID checks, alongside two individually reviewed examples. These were data-interpretation problems that required inspecting actual records, not just accepting generated SQL or fluent model text.

The known weakness I would flag to a teammate is **account identity**. WeLook groups observations by candidate domain and shows supporting or conflicting fields, but it does not resolve every legal business or verify current asset ownership. Its priority score is for investigation, not likelihood to buy. The offline LLM assessment has tracing and output checks, but no submitted labelled quality evaluation; its suggestions cannot be treated as validated. The next production step would be reviewed account enrichment, measured AI checks, and feedback from sales users.
