# How I built WeLook

I built WeLook as a small data platform with a sales workflow at the end, rather than starting with a dashboard. I first profiled the entire supplied compressed file as a stream and kept a seeded 5,000-row sample for fast iteration. That showed an important product risk: many records describe cloud or CDN infrastructure, so `org`, IP location, and vulnerability labels cannot simply become customer facts. I chose an external attack-surface monitoring sales use case and made account attribution and evidence review visible in the app.

My development loop was: write a narrow pipeline step, run it on the sample, inspect real counterexamples, then run it on the full source and reconcile counts. I used Codex to help draft Python ingestion, dbt SQL, Streamlit screens, tests, and documentation. `uv` made the environment repeatable; DuckDB and Parquet kept the 11.77-million-row job on one laptop. The full ingestion reconciled every source line, and the account build produced a compact serving snapshot. I kept the expensive work offline so the hosted app can be read-only.

AI saved the most time when turning a concrete data contract into working code and when suggesting checks around retries, evidence IDs, tracing, and costs. It cost more time where a plausible implementation could give a misleading sales conclusion. For example, the first score treated every vulnerability association similarly. Inspecting the nested source metadata showed that nearly all sampled associations were unverified, so I changed the model to keep and use that flag. Provider platforms caused a similar correction: matching a domain and certificate can still identify a shared service, not the business behind it. The preliminary v1/v2 eval exposed that same weakness in the LLM: v2 recalled only 2 of 9 draft `needs_review` cases. These were data-interpretation problems that required inspecting actual records and measured errors, not just accepting generated SQL or fluent model text.

The known weakness I would flag to a teammate is **account identity**. WeLook groups observations by candidate domain and shows supporting or conflicting fields, but it does not resolve every legal business or verify current asset ownership. Its priority score is for investigation, not likelihood to buy. A 25-case labelled set and traced offline LLM assessment make the ambiguous decisions measurable, but that small eval cannot establish production accuracy across all countries, hosting platforms, and service types. The next production step would be reviewed account enrichment and feedback from sales users.
