# How I built WeLook

I started by exploring the supplied compressed dataset without loading the whole file into memory. I first created a 5,000-row sample so I could understand the fields and test ideas quickly. I found that many records referred to cloud platforms, hosting companies, or shared infrastructure. Because of this, I decided that WeLook should help a salesperson choose what to investigate next instead of claiming that every signal belongs to a company.

My development process was simple: understand one part of the data, build a small version, check the output, and then improve it. Once the sample pipeline worked, I ran it on the complete dataset and compared the row counts between each layer. I used Python and PyArrow for streaming ingestion, Parquet for the Bronze and Silver files, DuckDB as the local warehouse, dbt for SQL transformations, and Streamlit for the application. I used `uv` to manage the Python environment and dependencies.

I used Codex throughout the project to help write Python, SQL, tests, documentation, and the Streamlit interface. It saved me the most time when creating the initial project structure, writing similar transformations, and finding edge cases that I had missed. For example, testing showed that domains with different letter casing could create duplicate evidence and that a source line number was not unique when more than one file was loaded.

I am more experienced in data engineering than LLM evaluation, so I kept AI out of the core scoring logic. Rules rank every candidate in a repeatable way. The LLM is a smaller offline step that reads selected evidence and suggests a short explanation and next research action. Some early notes sounded too confident when the evidence only showed a partial domain match. I therefore separated generation from publication and added checks for citations, cautious wording, source freshness, and review status. Each API call records the prompt version, model, token usage, estimated cost, response, and final decision.

I compared prompt versions v4 and v5 using 25 labelled examples. The comparison checks whether the model follows the decision policy and whether its wording passes the publication rules. The labels were proposed during development and still need independent human review, so I do not treat the result as proof that the model can detect real vulnerabilities. Keeping this limitation visible helped me avoid overstating the evaluation.

The main weakness I would flag to a teammate is company identity. WeLook groups observations by domain, but a domain does not always prove which business operates a service. A hosting provider or shared platform may appear in the evidence. Because of this, the application presents each result as a research priority and asks the user to verify the business, service operator, and technical finding before outreach. If I continued the project, I would add trusted company enrichment, independently reviewed evaluation labels, and feedback from real sales users.
